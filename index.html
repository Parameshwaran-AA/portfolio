Multi-Agent Systems · Code Generation

AutoDevX — five agents, one self-correcting loop

Takes a product requirement and returns an implementation plan, an architecture, executable Python, and a pytest suite. The hard part is not generation, it is what happens when the generated code fails its own tests.

Five agents run in sequence through a shared tool-execution layer. The Tester runs the suite for real rather than predicting a result, and a failure routes to the Debugger, which regenerates against the actual traceback and sends the patched code back through the tests. Retrieval over prior context runs on FAISS, with PostgreSQL holding run state.

Agentic AI · Retrieval

WearWise — recommendations that have to cite a source

Most recommenders answer from whatever the model absorbed in training. This one is constrained twice: it can only suggest clothes the user actually owns, and every style claim it makes has to come back to a retrieved source.

A ReAct loop decides between two tools on each turn, searching the wardrobe or retrieving fashion norms through agentic RAG, and keeps going until it can ground the recommendation. Uploaded photos are interpreted multimodally and written into the wardrobe, so the catalogue builds itself from what the user wears.

Data Engineering · Pipelines

DataPilot — pipelines that repair their own transformations

Ingestion breaks when the schema moves. The usual answer is a human rewriting the transformation every time a column is renamed or a type drifts. DataPilot puts schema discovery in front of the transformation and lets the pipeline correct itself.

Raw data arrives from files, APIs, object storage, and streams. An LLM step infers the schema, transformations validate against it, and a failure regenerates the transform instead of halting the DAG. Anomaly detection runs on the output and lineage is tracked across the whole path, so a bad number downstream can be traced to the row that caused it.

Backend Architecture · Concurrency

Event Booking — two people, one seat, one winner

Ticketing is a concurrency problem wearing a CRUD costume. Two requests read the same seat as available in the same millisecond and both write a booking. Pessimistic locking solves it and destroys throughput at exactly the moment you have traffic.

This backend uses optimistic locking instead: both writes are allowed to proceed, the version check rejects the loser, and the client retries against fresh state. Hot read paths are served from Redis rather than the database, and JWT handles auth on every request. Integration tests cover the contended path, not just the happy one.

Full Stack · Search

Fable — one request, three data stores

A social storytelling platform where the interesting problem is routing. Full-text search, the document store, and the hot cache all want the same request for different reasons, and the API layer has to decide which one answers.

GraphQL fronts the whole thing so a client asks for exactly the fields it needs in one round trip instead of chaining REST calls. ElasticSearch handles full-text querying across stories, MongoDB holds the documents, and Redis keeps the hot reads off both. The stack runs under Docker Compose.
